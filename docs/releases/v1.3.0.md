# ResolveOps v1.3.0 — Expanded customer resolution workflows

This release adds two customer problems to the existing controlled operations path: an incorrect
return-refund amount and a captured charge on a cancelled order. They are not extra demo screens.
Each starts from a stored complaint, reads current business records and policy, requests the bounded
specialist graph when live inference is configured, and hands only a typed recommendation to the
deterministic control plane.

## Workflow behavior

- **Incorrect refund amount:** computes returned-item value, subtracts completed return refunds and
  proposes only the remaining balance. No prior refund, inconsistent items or insufficient capture
  allocation stops for review.
- **Cancelled order still charged:** requires a cancelled order and exactly one linked, full captured
  payment for its explicit obligation. Partial or multiple allocations stop for review.
- Both require separate approval, current-evidence revalidation, idempotent submission, a provider
  status event and a fresh read before the case can resolve.
- Demo scenarios `CASE-DEMO-I` and `CASE-DEMO-J` contain fictional records for the two paths.

## Verification

- Focused unit and end-to-end workflow tests cover proposals, safety stops, approval, typed action,
  provider settlement and final verification.
- Browser tests drive both seeded scenarios through the real operator console.
- Existing duplicate-charge, return-refund, combined customer and Employee IT behavior remains in
  the full regression suite.

## Safety boundary

All sandbox records and actions are synthetic. Models remain advisory and cannot approve or issue
a refund. No bank, CRM or customer portal is connected. A public deployment is evidence only after
its `/health/build` revision, schema and fresh workflow results are recorded separately.
